# TL-Radar

Внутренний дешборд тим лида MIFCOM для отслеживания задач: кто чем занят,
где, с каким статусом и сколько времени на это ушло. Next.js (App Router,
TypeScript) + Supabase (Postgres/Auth/RLS/Edge Functions/pg_cron) + Vercel.

Контекст и история:

- [`tl-radar.html`](./tl-radar.html) — исходный прототип с бизнес-логикой
  (переходы статусов, расчёт чистого времени выполнения), с которого
  начинался перенос на бэкенд.
- [`tl-radar-backend-plan.md`](./tl-radar-backend-plan.md) — исходный план
  миграции на Supabase. **Исторический документ**: описывает схему и
  решения (email-логин, роль `viewer` при регистрации, одиночный
  исполнитель) до начала разработки — часть из них впоследствии изменилась.
  Актуальное описание — этот README.

## Стек

- Next.js 16 (App Router, TypeScript, Server Actions, Server Components)
- Supabase (Postgres + Auth + RLS + Edge Functions + pg_cron + pg_net)
- Vercel (хостинг)
- `@dnd-kit/core` (drag & drop в канбане)
- `lucide-react` (иконки)
- `exceljs` (генерация `.xlsx` для экспорта)

Сторонних UI-китов и чарт-библиотек нет: вся стилизация — на CSS-переменных
в `app/globals.css`, оба графика в аналитике нарисованы вручную (`<div>` с
процентной шириной и SVG, без сторонних зависимостей).

## Функциональность

- **Задачи**: канбан по статусам (`waiting` / `in_progress` / `paused` /
  `done`), дедлайн, описание, место, чистое время выполнения с учётом пауз.
  Мягкое удаление (`deleted_at`) — строка не стирается физически.
- **Множественные исполнители**: у задачи может быть несколько
  исполнителей одновременно; у каждого своя история добавления/снятия
  (`task_assignees`).
- **Проекты**: необязательная группировка задач (`/projects`) — название,
  необязательные описание/место/ответственный/цвет (`ColorPicker`, для
  визуального различения проектов на карточках). Слайд-овер деталей
  проекта показывает журнал изменений (тот же `activity_log`, что и у
  задач).
- **Оценка времени**: необязательная оценка в минутах на задачу,
  индикатор «факт / оценка» на карточке и в архиве.
- **Аналитика**: `/analytics` — время каждого человека «на задачах» в
  сравнении с доступным рабочим временем за период (7/30/90 дней).
- **Автопауза**: в 16:00 по Мюнхену все задачи в статусе «в процессе»
  автоматически переводятся в «пауза» (Edge Function + pg_cron).
- **Рабочие часы**: смена статуса задачи и накопление времени возможны
  только с 07:30 до 16:00 по Мюнхену.
- **Просроченные дедлайны**: задача с дедлайном в прошлом (и статусом не
  «выполнено») подсвечивается красным бейджем/рамкой на карточке; в колонках
  канбана просроченные задачи идут первыми, затем по близости дедлайна,
  задачи без дедлайна — в конце. В архиве завершённые с опозданием задачи
  помечены «просрочено на …».
- **Поиск и фильтры**: над канбаном (и в архиве, без фильтра по статусу) —
  текстовый поиск по названию/описанию, фильтр по исполнителю (мультивыбор),
  проекту, приоритету, наличию дедлайна/просрочке. Состояние — в URL search
  params (`?assignee=<id>&priority=high`), фильтрация целиком на сервере
  (Server Component читает `searchParams`), поэтому ссылка на отфильтрованный
  вид — шарабельная. Пустой результат показывает отдельный EmptyState со
  ссылкой на сброс фильтров.
- **Drag & drop в канбане**: карточку можно перетащить между колонками
  (`waiting` ↔ `in_progress` → `paused`), это вызывает тот же серверный
  экшен `setStatus`, что и кнопки статуса — рабочие часы и допустимые
  переходы (`VALID_KANBAN_TRANSITIONS`, подмножество кнопочных переходов:
  канбан не даёт колонки для прямого броска в «выполнено») проверяются
  так же строго. Оптимистичный UI: карточка переезжает в колонку сразу,
  откатывается назад с алертом при отказе сервера (например, вне рабочих
  часов). Колонка, в которую бросить нельзя, визуально приглушена; при
  наведении над допустимой целью — подсвечивается. Кнопки статуса
  остаются основным доступным способом смены статуса (drag не размечен
  как доступный элемент — нет клавиатурного перетаскивания).
- **Комментарии к задачам**: лента в слайд-овере задачи (автор, время),
  форма добавления, мягкое удаление — автор своего комментария или admin
  любого. Видны всем авторизованным. Счётчик (иконка + число) на карточке
  в канбане. Каждое добавление пишется в журнал задачи как `comment_added`.
- **In-app уведомления** (Этап 5A): колокольчик в топбаре со счётчиком
  непрочитанных, обновляется поллингом раз в 30 сек через обычный Route
  Handler `app/api/notifications` (не Server Action — см. ниже, почему).
  Событие создаётся всем затронутым, кроме автора действия: назначение/
  снятие исполнителя, новый комментарий; отдельно раз в час в рабочие часы
  Edge Function `notify-deadline-soon` проверяет задачи с дедлайном сегодня
  и уведомляет каждого исполнителя (без дублей, если уведомление уже есть
  и не прочитано). Клик по уведомлению помечает его прочитанным и ведёт на
  дашборд/архив (в зависимости от статуса задачи) — отдельной страницы
  задачи в приложении нет. «Прочитать все» — одной кнопкой.
- **Чек-листы в задачах**: пункты в слайд-овере задачи — добавление,
  отметка выполнения, переупорядочивание стрелками (без DnD), мягкое
  удаление. Отметка пункта не меняет статус задачи и не трогает учёт
  времени — это просто `done`. Прогресс («2/5») на карточке в канбане.
  Добавление пункта пишется в журнал задачи как `checklist_item_added`;
  отметка/удаление/перестановка — нет (слишком частое событие для лога,
  как паузы не пишутся отдельно от смены статуса).
- **Шаблоны задач** (Этап 7): страница `/templates` — список сохранённых
  шаблонов с мягким удалением. Шаблон создаётся только из существующей
  задачи кнопкой «Сохранить как шаблон» в слайд-овере (снимок полей —
  название, описание, место, оценка времени, приоритет, иконка, проект,
  плюс список названий пунктов чек-листа); шаблоны не редактируются и не
  создаются вручную — это осознанное решение по роадмапу, а не пропуск.
  На `/dashboard/new` появляется выпадающий список «Из шаблона»: выбор
  шаблона предзаполняет форму создания новой задачи (через query-параметр
  `?template=id`, без потери обычной формы редактирования) и копирует
  пункты чек-листа в новую задачу при сохранении. Выбор шаблона — это
  всегда создание новой задачи, а не редактирование существующей (форма
  корректно показывает "Добавить задачу", а не "Сохранить изменения",
  даже когда поля предзаполнены из шаблона).
- **Повторяющиеся задачи** (Этап 8): на странице `/templates` — блок
  «Повторяющиеся правила». Правило ссылается на шаблон (Этап 7) и создаёт
  из него новую задачу по расписанию — ежедневно (по будням), еженедельно
  (конкретный день пн-пт) или ежемесячно (число месяца; если оно выпадает
  на выходной — переносится на ближайший рабочий день). Учитываются
  только рабочие дни — решение согласовано с заказчиком перед
  реализацией. `pg_cron` раз в час дёргает Edge Function
  `recurring-tasks`; сама функция решает, наступило ли начало рабочего
  окна по Мюнхену (07:30-08:30), находит правила с `next_run_at <=
  сегодня`, создаёт задачу (со снимком полей и чек-листа шаблона,
  исполнителем — автор правила) и сразу сдвигает `next_run_at` — это и
  есть защита от дублей при повторных срабатываниях крона в течение
  одного дня. Правило можно временно отключить («Активно») без удаления
  — тогда оно просто не создаёт задач, но остаётся в списке.
- **Командная палитра** (Этап 9, бэклог): `Cmd/Ctrl+K` (или иконка поиска в
  топбаре) открывает окно с быстрым переходом по разделам и быстрым
  созданием задачи. Если введённый текст совпадает с названием раздела —
  он в списке первым и `Enter` переходит на страницу; если нет ни одного
  совпадения — единственный вариант «Добавить задачу: …», `Enter` создаёт
  задачу с этим названием и назначает исполнителем текущего пользователя
  (без остальных полей — использовать обычную форму, если нужны детали).
  Порядок вариантов (навигация раньше быстрого создания) — осознанное
  решение: иначе `Enter` при наборе названия раздела мог бы случайно
  создать мусорную задачу вместо перехода.
- **Табличный вид + сохранённые представления** (Этап 10, бэклог): на
  дашборде переключатель «Канбан / Таблица» (иконки рядом с фильтрами) —
  таблица со всеми полями (статус, проект, приоритет, дедлайн, оценка,
  исполнители) и кликабельными заголовками столбцов для сортировки на
  клиенте; действия в строке (старт/пауза/готово, изменить, удалить,
  история) — те же, что и на карточке канбана. Режим отображения
  хранится в query-параметре `view=table`, поэтому переживает обновление
  страницы и попадает в сохранённые представления. «Сохранённые
  представления» — именованные пресеты, привязанные к пользователю
  (таблица `saved_views`, RLS только для владельца — единственное место
  в проекте с личными, не общекомандными настройками): сохраняют query
  string дашборда целиком (все фильтры + режим отображения), поэтому при
  выборе представления просто переходим на `/dashboard?<сохранённая
  строка>` без пересборки отдельных параметров.
- **Аналитика v2** (Этап 11, бэклог): на странице `/analytics` под
  существующим блоком «время по людям» — два новых раздела. «Распределение
  задач по статусам» — SVG-график (без сторонних чарт-библиотек):
  ежедневный срез количества задач в каждом статусе за выбранный период,
  восстановленный из `activity_log.event_type = 'status_changed'` (это
  упрощённый снепшот «кто где сейчас», а не классический CFD с
  кумулятивными приходами в каждый этап — сознательное упрощение).
  «Точность оценок» — таблица по людям: среднее отношение фактического
  чистого времени в работе (`netDuration`, тот же показатель, что уже
  показывается на карточке и в архиве) к `estimated_minutes`, только по
  завершённым задачам с указанной оценкой; отношение приписывается каждому
  текущему исполнителю задачи.
- **Экспорт в CSV/XLSX** (Этап 12, бэклог): на страницах `/archive` и
  `/analytics` — кнопки «CSV» / «XLSX» рядом с фильтрами (архив) или
  переключателем периода (аналитика). Экспорт архива уважает те же
  активные фильтры, что показаны на экране (те же `parseTaskFilters` /
  `matchesTaskFilters`, что и сама страница); экспорт аналитики — те же
  `days` (7/30/90). Оба формата отдаются одним и тем же обычным Route
  Handler'ом (`GET /api/export/archive`, `GET /api/export/analytics`,
  `?format=csv|xlsx`) — строки собираются один раз и либо превращаются в
  CSV-текст (с BOM для корректной кириллицы в Excel), либо в `.xlsx`-буфер
  через `exceljs`. Библиотека выбрана осознанно вместо более popular `xlsx`
  — та на момент подключения несла две неисправленные (`No fix available`)
  уязвимости high-severity (prototype pollution, ReDoS) по данным `npm
  audit`.
- **@упоминания в комментариях + наблюдатели** (Этап 13, бэклог): при
  вводе `@` в поле комментария — выпадающий список подходящих
  пользователей (по имени или юзернейму), `↑↓`/`Enter`/`Tab` для выбора,
  `Esc` — закрыть. Вставляется `@username` (юзернеймы уникальны и уже
  используются для входа — надёжный токен для разбора текста, в отличие
  от имени, которое может повторяться); при отображении комментария
  токен резолвится обратно в отображаемое имя и подсвечивается. При
  отправке комментария упомянутые пользователи получают уведомление
  типа `mention` (отдельно от `comment`, который по-прежнему уходит
  исполнителям задачи). «Наблюдатели» — кнопка (глаз) в слайд-овере
  задачи: подписка на уведомления обо всех новых комментариях к этой
  задаче независимо от назначения (таблица `task_watchers`; читают все
  авторизованные, как `task_assignees` — автору комментария нужно видеть
  полный список наблюдателей, добавлять/убирать может только сам
  пользователь).
- **Метки, календарный вид, WIP-лимиты** (Этап 14, бэклог):
  - *Метки/теги* — командные (как проекты), с цветом из фиксированной
    палитры (`labels`/`task_labels`, связь многие-ко-многим). Назначаются
    прямо в форме задачи (мульти-select с инлайн-созданием новой метки —
    отдельной страницы управления метками нет); отображаются пилюлями на
    карточке/в таблице/в архиве; фильтр по меткам — рядом с фильтром по
    исполнителям.
  - *Календарный вид* — третий режим дашборда (`?view=calendar`) рядом с
    канбаном/таблицей: месячная сетка, задачи показаны в ячейке своего
    дедлайна (без дедлайна — не попадают в календарь, видны в
    канбане/таблице по-прежнему); `←`/`→` листают месяцы (`?month=YYYY-MM`).
  - *WIP-лимиты* — максимум задач одновременно в каждой колонке канбана
    (`wip_limits`, по строке на статус; изначально только
    waiting/in_progress/paused, миграция `0033` добавила `done`/«Erledigt»
    — четвёртое поле на макете админки, `null` — без ограничения).
    Настраиваются на `/admin` (только admin); при попытке перевести задачу
    в колонку на лимите — что через drag-and-drop, что кнопкой статуса —
    сервер отклоняет переход с понятной ошибкой (проверка в том же
    `setStatus`, что и до этого обслуживал все переходы статуса — но сама
    проверка условием ограничена статусами `waiting`/`in_progress`/`paused`,
    `done` в неё не входит). Колонки «Erledigt» в канбане не существует —
    завершённые задачи сразу уезжают в архив, так что лимит для `done`
    нигде не проверяется и физически ни на что не влияет: поле в форме и
    строка в таблице настраиваются, сохраняются, но эффекта не имеют —
    задокументированное несоответствие макету, а не баг.
- **PWA** (Этап 15, бэклог): `app/manifest.ts` (иконки — сгенерированный
  SVG-радар на брендовом красном, 192/512 + maskable-вариант для Android),
  `theme-color` (свой на светлую/тёмную тему), `apple-touch-icon`.
  Service worker (`public/sw.js`) регистрируется только внутри
  авторизованной части приложения (не на `/login`) — кеширует статику
  `_next/static` и при потере сети на переходе между страницами отдаёт
  заглушку `public/offline.html`; API/Server Action-запросы (включая GET
  к динамическим данным вроде уведомлений) никогда не кешируются, чтобы не
  показать устаревшие задачи. `proxy.ts` явно исключает
  `manifest.webmanifest`/`sw.js` из редиректа на `/login` — иначе браузер
  не смог бы их получить до входа.
- **i18n**: три языка интерфейса — de (по умолчанию) / en / ru.
- **Тёмная тема**: переключатель в топбаре, персистентность через cookie.
- **Toast-уведомления об ошибках** (оптимизация, этап 4): вместо `alert()` —
  `components/ToastProvider.tsx` (без сторонних библиотек), стек
  снизу справа, авто-скрытие через 5 с, закрытие кликом, обе темы. Тексты
  ошибок уже локализованы на сервере (server actions резолвят `dict` по
  локали пользователя) — клиент просто показывает `result.error` как есть.
- **Админ**: сброс пароля и удаление любого пользователя, настройка
  WIP-лимитов канбана (см. «Роли» ниже).

## Роли

Решение по ролям (осознанное, не пересматривается без явного запроса):

- **editor** — единственная роль, назначаемая при самостоятельной
  регистрации. Все зарегистрированные пользователи могут
  создавать/редактировать/удалять задачи, менять их статус, управлять
  проектами. Роль `viewer` не используется — это не баг и не недоделка, а
  сознательный выбор (см. миграцию `0006_remove_viewer_role.sql`).
- **admin** — не выбирается самостоятельно при регистрации. Назначается
  вручную через Supabase Dashboard → Table Editor (или SQL editor):
  ```sql
  update profiles set role = 'admin' where id = '<uuid пользователя>';
  ```
  UI для самоназначения `admin` сознательно не делается. После назначения
  роли админ получает доступ к странице `/admin` (пункт «Admin» в топбаре)
  для сброса пароля/удаления любого пользователя и настройки WIP-лимитов
  канбана (детали — ниже).

Доступ к `/analytics` регулируется отдельно, через именованную константу
`STATS_MIN_ROLE` в `lib/logic/access.ts` (сейчас `'editor'` — то есть видно
всем; решение об ограничении только ролью `admin` откладывается на потом и
требует правки только этой константы).

### Управление пользователями и WIP-лимитами (страница `/admin`)

- `lib/supabase/admin.ts` — клиент Supabase на service role key
  (`SUPABASE_SERVICE_ROLE_KEY` в `.env.local`, без префикса `NEXT_PUBLIC_`,
  используется только внутри Server Actions, никогда не попадает в
  клиентский бандл).
- `app/(app)/admin/actions.ts`:
  - `resetUserPassword(userId, newPassword)` — проверяет, что текущий
    пользователь имеет роль `admin` (иначе редирект на `/dashboard`), затем
    вызывает `supabaseAdmin.auth.admin.updateUserById`.
  - `deleteUser(userId)` — тем же способом (service role,
    `auth.admin.deleteUser`) безвозвратно удаляет пользователя; отказывает,
    если admin пытается удалить сам себя (`DeleteUserButton` показывается
    для всех пользователей, кроме текущего). Внешние ключи на
    `profiles(id)` — `on delete set null`/`cascade` по месту (см. `0014`),
    поэтому удаление не блокируется историей задач/комментариев/пауз.
- `app/(app)/admin/page.tsx` — список всех пользователей (имя + роль) с
  формой сброса пароля и кнопкой удаления у каждого, плюс форма WIP-лимитов
  канбана (`WipLimitsForm`, см. «Метки, календарный вид, WIP-лимиты» выше —
  включая четвёртое поле `done`, которое ни на что не влияет); недоступна
  без роли `admin`.
- На Vercel обязательно должна быть задана переменная окружения
  `SUPABASE_SERVICE_ROLE_KEY` (Project Settings → Environment Variables),
  иначе `/admin` будет падать при попытке сброса пароля или удаления.

## Аутентификация

Регистрация: имя, фамилия, юзернейм, пароль. Вход: **только юзернейм и
пароль** — без email, без имени/фамилии. Имя и фамилия остаются в
`profiles.name` исключительно для отображения и выбора исполнителя на
задачу, в авторизации не участвуют.

Supabase Auth внутри всегда требует email-идентификатор, поэтому он
выводится детерминированно из нормализованного юзернейма через SHA-256
(`lib/auth/synthetic-email.ts`) — пользователь его никогда не видит и не
вводит. `profiles.username` уникален (`profiles_username_format`:
латиница/цифры/`.`/`_`, 3–32 символа).

Детали отдельных миграций:

- **`0002`**: ключ сервисной роли для авторизации вызова Edge Function
  хранится в Supabase Vault под именем `tl_radar_service_role_key`
  (заводится отдельно, не в миграции — секреты в git не хранятся).
- **`0008`**: `deleted_at` — мягкое удаление, строка не стирается
  физически, просто перестаёт показываться в дешборде/архиве;
  `task_pauses.created_by` — `null`, если пауза автоматическая
  (`auto = true`).
- **`0009`**: RLS — читать могут все авторизованные, писать (включая
  мягкое удаление) — только editor/admin. Страница `/projects` доступна
  всем зарегистрированным.
- **`0010`**: существующие одиночные `assignee_id` перенесены в
  `task_assignees` с `added_at = tasks.created_at`. Важное правило (нужно
  для аналитики, `0011`+): время засчитывается исполнителю только с
  момента его фактического добавления (`added_at`), не задним числом —
  поэтому при повторном добавлении ранее снятого исполнителя создаётся
  новая строка с новым `added_at`, а не переиспользуется старая.
- **`0011`**: используется только для индикатора «оценка vs факт» —
  переиспользует существующий `accumulatedInProgressDuration()`, новой
  бизнес-логики учёта времени не вводит. Полоса прогресса меняет цвет на
  «перерасход» (`--brand`), если факт превышает оценку.
- **`0015`**: у уже существующих на момент миграции аккаунтов юзернейм
  бэкфиллится из нормализованного имени + короткий суффикс от `id`
  (например, `romanholovachov5f9a2f`) — это одноразовый шаг для старых
  строк, новые пользователи выбирают юзернейм сами при регистрации.
- **`0019`**: мягкое удаление комментария — автор своего или admin любого
  (RLS-политика на `update`, не сервисная проверка ролей). Значение
  `comment_added` добавлено в `event_type` пересозданием check-constraint
  из `0017` (менять уже применённую миграцию нельзя — один шаг, одна
  миграция, по конвенции проекта).
- **`0020`/`0021`**: чтение уведомлений (счётчик, список) в
  `NotificationBell` идёт через обычный Route Handler
  (`app/api/notifications`), а не через Server Action — это не стиль, а
  зафиксированный e2e фикс: фоновый поллинг раз в 30 сек, вызванный как
  `'use server'`-функция прямо из клиентского компонента, оказался
  подвержен той же гонке RSC/router-пейлоадов, что и `router.replace()` в
  Stage 2 (`TaskFilterBar`) — ответ пустого поллинга иногда «перебивал»
  свежий payload другого Server Action (например, редирект после создания
  проекта), и страница откатывалась к устаревшему состоянию. Обычный
  `fetch()` к Route Handler полностью независим от этого механизма.
  Мутации (`markRead`/`markAll`) остаются в том же Route Handler (POST),
  не в Server Actions — для единообразия одного эндпоинта. Тот же приём —
  обычный `GET`/`POST` вместо Server Action — по той же причине применён
  ещё в двух местах, где компонент уже вызывает несколько `'use server'`
  функций одновременно: `app/api/watch` (наблюдение за задачей из
  `TaskDetailPanel`, открытого вместе с логами/комментариями/чек-листом) и
  `app/api/mentionable-profiles` (список пользователей для автодополнения
  `@упоминаний` в `CommentList`, там же).
- **`0030`/`0031`** (оптимизация, этап 3): фоновый поллинг раз в 30 сек
  заменён на Realtime-подписку (`postgres_changes` INSERT по
  `notifications`, фильтр `recipient_id=eq.<uid>`) — счётчик у колокольчика
  обновляется по событию, без опроса в фоновой вкладке. Поллинг остаётся
  как fallback, если канал не поднялся (`status !== 'SUBSCRIBED'`), и
  срабатывает только пока вкладка видима. `GET .../notifications?full=1`
  вместо 2 последовательных запросов (`notifications`, затем `tasks` по
  `task_id`) использует RPC `get_my_notifications()` — `task_id` намеренно
  без FK (`0020`), поэтому обычный PostgREST-embed не выразим, вместо
  этого один SQL-запрос с `LEFT JOIN` внутри функции.

## Бизнес-логика времени (перенесена из прототипа, затем расширена)

- `waiting → in_progress`: проставляется `started_at` (один раз).
- `in_progress → paused`: открывается запись в `task_pauses`
  (`paused_at`, `resumed_at = null`).
- `paused → in_progress`: закрывается открытая пауза (`resumed_at = now`).
- `→ done`: закрывается открытая пауза (если была), проставляется
  `completed_at`.
- Чистое время выполнения в архиве: `completed_at − started_at` минус
  сумма длительностей пауз (`netDuration`).
- Смена статуса и накопление времени заблокированы вне рабочих часов
  (07:30–16:00 по Мюнхену, `isWithinWorkHours`); вне этого окна «текущее
  время» для таймеров замораживается на моменте последнего 16:00
  (`effectiveNow`).

`accumulatedInProgressDuration(task, pauses, end)` — суммарное время в
статусе `in_progress` (за вычетом закрытых пауз) — построена поверх
экспортируемого `inProgressIntervals()` (список интервалов времени
in_progress), который переиспользуется и в аналитике для пересечения с
окном присутствия конкретного исполнителя.

См. `lib/logic/tasks.ts`.

## Аналитика

- `lib/logic/analytics.ts`:
  - `availableWorkingMs(rangeStart, rangeEnd)` — суммарное доступное
    рабочее время (07:30–16:00 по Мюнхену за каждый день диапазона),
    единый бенчмарк для сравнения.
  - `computePersonStats(...)` — время каждого человека «на задачах» за
    период: пересечение `inProgressIntervals()` задачи с окном
    `[added_at, removed_at]` каждого назначения из `task_assignees`,
    включая уже снятые назначения (кредит за время до снятия).
- Страница `/analytics` — бар-чарт (свёрстан вручную на `<div>` с
  процентной шириной, без сторонних чарт-библиотек) «отработано» по
  каждому человеку с опорной линией «доступно», плюс таблица с точными
  цифрами.
  Переключатель периода (7/30/90 дней) через `?days=`.
- Доступ регулируется `STATS_MIN_ROLE` (`lib/logic/access.ts`), см. «Роли».

## E2E-тесты (Playwright)

28 тестов в четырёх файлах на момент написания:

- `e2e/golden-path.spec.ts` (22) — не только базовый путь (регистрация,
  проект, задача с несколькими исполнителями и оценкой времени,
  редактирование, валидация «нужен хотя бы один исполнитель», мягкое
  удаление, гейтинг смены статуса по рабочим часам — детерминированно,
  тест проверяет, что доступно ровно одно из двух состояний независимо от
  времени суток запуска), но и большую часть бэклога: drag & drop в
  канбане, комментарии, уведомления (назначение/снятие/комментарий/
  упоминание), чек-листы, шаблоны и повторяющиеся правила, командную
  палитру, табличный вид и сохранённые представления, аналитику v2
  (CFD-график, точность оценок), экспорт CSV/XLSX, метки и календарный
  вид, PWA-манифест и service worker. Загрузку `/projects` + `/analytics`
  без ошибок консоли — тоже.
- `e2e/kanban-dnd-advanced.spec.ts` (2) — перетаскивание карточки с
  клавиатуры (`@dnd-kit` поддерживает это из коробки) и блокировку второго
  drag, пока предыдущая смена статуса ещё не подтвердилась сервером.
- `e2e/overlay-accessibility.spec.ts` (3) — слайд-овер/командная палитра/
  панель уведомлений: ловушка фокуса, `Escape`, возврат фокуса на
  триггер при закрытии, и что модальный слайд-овер блокирует скролл фона,
  а немодальная панель уведомлений — нет.
- `e2e/realtime-notifications.spec.ts` (1) — что счётчик уведомлений
  обновляется в уже открытой вкладке без перезагрузки (через Realtime
  `postgres_changes`, миграция `0030`); тест сам знает и явно
  документирует, что в песочнице с проксированным исходящим трафиком
  `wss://`-соединение может не подняться, и в этом случае полагается на
  30-секундный резервный поллинг — поэтому у него увеличенный таймаут.

### Как прогнать e2e локально

Тесты регистрируют пользователей и создают задачи по-настоящему — гонять их
по боевой базе нельзя. Нужен локальный Supabase-стек:

```bash
supabase start   # поднимает Postgres + Auth + Storage + Edge Functions в Docker
```

Команда печатает `API_URL`, `ANON_KEY` и `SERVICE_ROLE_KEY` локального стека
(их же можно получить повторно через `supabase status`). На время тестов
временно заменить ими три переменные в `.env.local` (значения для боевой базы
из `.env.example` — отложить в сторону, потом вернуть обратно):

```
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<ANON_KEY из вывода supabase start>
SUPABASE_SERVICE_ROLE_KEY=<SERVICE_ROLE_KEY из вывода supabase start>
```

Дальше (playwright.config.ts сам поднимет `npm run dev`, если
`PLAYWRIGHT_BASE_URL` не задан):

```bash
npm run test:e2e
```

Тесты регистрируют одноразовых пользователей со случайными именами и не
полагаются на существующие данные — безопасно гонять повторно. Между
прогонами данные в локальной базе накапливаются (тесты не удаляют за
собой). Чтобы начать с чистого листа — `supabase db reset` (заново
накатывает все 33 миграции; это заодно и есть проверка, что миграции
воспроизводимы на пустой базе).

На Windows с Docker Desktop, поставленным в `%LOCALAPPDATA%` (не в
`Program Files`), `supabase start` может не находить `docker`, даже если он
только что установлен и виден в системном PATH — новый PATH не подхватывается
уже открытыми терминалами. Добавить путь к `docker.exe` в PATH текущей сессии
или открыть новый терминал.

**Известная нестабильность.** До стабилизации `e2e/helpers.ts`/тестов
падало 10-13 из 28 почти на каждом прогоне на чистой базе, почти всегда с
одним и тем же симптомом: клик по ссылке навигации или кнопке после
полной перезагрузки страницы (редирект из Server Action, а не клиентский
переход) иногда не производит ожидаемого эффекта, хотя тот же сценарий
вручную в браузере проходит надёжно — похоже на гонку между кликом и
завершением гидратации React (тот же класс проблемы, что уже был найден и
частично исправлен раньше — `goToNewTaskFromTaskManager` в
`e2e/helpers.ts` — но не везде). Добавлена короткая пауза после каждой
полной навигации (`page.goto`/`page.waitForURL`) по всем четырём файлам.
После этого на нескольких подряд прогонах результат стабильно доходил до
18-21 из 28.

Полностью детерминированного результата на каждый запуск это не
гарантирует: на затянутой сессии (несколько часов, много прогонов подряд
на одной машине с постоянно поднятым Docker-стеком) периодически всё ещё
падает несколько тестов, каждый раз в разных местах — похоже на
исчерпание ресурсов машины при таком режиме, а не на баг конкретного
теста. Отдельно `realtime-notifications.spec.ts` может падать по причине,
описанной в самом тесте (см. выше) — это ограничение песочницы, не код
приложения. Если `test:e2e` падает — для начала стоит перепрогнать на
свежем `supabase db reset` и, по возможности, на не занятой параллельно
машине, прежде чем разбирать конкретный тест как реальную поломку.

Если в окружении предустановлен только полный Chromium (не
`headless_shell`-вариант, который Playwright может ожидать для другой
сборки) — задать `PLAYWRIGHT_CHROMIUM_PATH=/path/to/chrome` явно.
