# TL-Radar — редизайн v2 «один в один по скриншотам»

Файл-задание для новой сессии Claude Code. Самодостаточный: не требует контекста
предыдущего чата. Промпты для каждого этапа — в блоках кода, копируются как есть.

---

## 0. Как пользоваться этим файлом

1. Открой новую сессию в репозитории `FLAIR-soft/TL-Radar`.
2. Скопируй промпт нужного этапа (раздел «Этапы») в чат.
3. Клод читает `design/redesign-v2/PLAN.md` (этот файл) + нужные скриншоты и делает **только свой этап**.
4. Проверяешь результат → мержишь → переходишь к следующему этапу.

Этапы идут по возрастанию риска. Каждый — отдельный PR, чтобы можно было
остановиться/откатить в любой момент, не потеряв остальное.

## 2. Контекст проекта (чтобы не изучать заново)

- **Стек:** Next.js 16 (App Router, Turbopack), React 19, TypeScript, Supabase.
- **Стилей-фреймворков нет.** Только `app/globals.css` + CSS-переменные. Tailwind
  не используется, новые зависимости не добавлять.
- **Иконки:** `lucide-react`, `strokeWidth={1.75}`.
- **Шрифт:** Archivo (подключён через `next/font/google` в `app/layout.tsx`,
  проброшен в `--sans`). Моно-цифры: класс `.mono` (уже с `tabular-nums`).
- **i18n:** три языка, `lib/i18n/dictionaries/{de,en,ru}.ts`. Тип `Dictionary`
  выводится из `ru.ts` — **новый ключ надо добавить во все три файла**, иначе
  `next build` упадёт на типах.
- **Данные:** серверные компоненты + серверные экшены. Мутации — через
  `app/(app)/**/actions.ts`.
- **Проверка:** `npm run build` и `npm run lint` должны быть зелёными.
  `npm ci` — если нет `node_modules`.

### Локальный визуальный прогон (без Supabase)

Ключей Supabase в песочнице нет, залогиниться нельзя. Проверять визуал так:
собрать статический HTML с нужной разметкой и **реальным** `app/globals.css`,

На скриншотах есть вещи, которые **прямо отменяют решения, принятые в коде
раньше и осознанно**. Заказчик сказал «хочу один в один», поэтому по умолчанию
**побеждает скриншот**. Но каждый такой откат должен быть явным и упомянут в
описании PR — чтобы никто потом не гадал, почему это вернулось.

| # | Что на скриншоте | Что сейчас в коде | Решение |
| --- | --- | --- | --- |
| K1 | Вкладка **«Neue Aufgabe»** в шапке | Убрана намеренно («Правки UI, этап 5»), на неё ведёт кнопка на Task-Manager | Вернуть вкладку. Кнопку на Task-Manager **оставить** |
| K2 | **Две кнопки CSV и XLSX** | Объединены в один `ExportMenu` с выпадашкой («Правки UI, этап 2») | Вернуть две кнопки. `ExportMenu` удалить из архива и аналитики |
| K3 | Аналитика: **«GEARBEITET · % der verfügbaren Zeit»**, 38 Std из 42 = 90 % | Инвертировано на «свободную ёмкость» («Правки UI, этап 6»): те же данные показываются как «% frei» | Вернуть прямую шкалу (отработанное время). Правится и текст подзаголовка, и `remainingCapacityPercent` |
| K4 | Левая полоса карточки задачи = **приоритет** | Полоса = цвет проекта (приоритет вынесен в пилюлю) | На скриншоте `03` у карточки «Serverraum Umbau» полоса оранжевая при приоритете «Hoch» → полоса = приоритет. Вернуть приоритет на полосу, пилюлю приоритета **оставить** |

## 5. Формат таймеров — разобрать отдельно, это ловушка

На скриншотах **два разных формата**, и путать их нельзя:

| Где | Формат | Пример со скриншота |
| --- | --- | --- |
| Живой таймер, задача **в работе** | `Ч:ММ:СС` | `1:24:08` (скрин `03`) |
| Живой таймер, **ожидание / пауза** | `Ч:ММ` | `215:46`, `6:12`, `0:42` (скрины `03`, `05`) |
| Длительности и оценки **везде остальное** | старый словесный | `3 Std 05 Min`, `Schätzung 3 Std`, `47 Min` (скрины `08`, `05`) |

Вывод: **`fmtDuration()` не трогать.** Она обслуживает архив, экспорт в CSV/XLSX
и оценки — там формат остаётся словесным, как на скрине `08`. Нужна **новая**
функция рядом с ней (например `fmtTimer(ms, withSeconds)`), которая
используется только в живых таймерах карточки и панели задачи.

Менять `fmtDuration` — сломает экспорт и e2e-тесты.

**Делать:**

- Верстать на существующих CSS-переменных из `app/globals.css`.

- Гонять `npm run build` и `npm run lint` перед коммитом.
- Проверять визуально (см. раздел 2) и прикладывать вывод в отчёт.
- Если скриншот и текущая логика противоречат — сверься с разделом 3; если случая там нет, **спроси**.

**Не делать:**
- ❌ Не менять бизнес-логику: расчёт времени, рабочие часы 07:30–16:00, правила
  переходов статусов, права доступа, `revalidatePath`, серверные экшены —
  если этап явно этого не требует.
- ❌ Не трогать `fmtDuration()` (см. раздел 5).
- ❌ Не менять схему БД без отдельного этапа с миграцией.
- ❌ Не добавлять зависимости (никаких chart-библиотек, Tailwind, UI-китов).
  Графики — на `div`/`svg` руками.
- ❌ Не хардкодить hex-цвета в компонентах — только переменные.
- ❌ Не переписывать то, что не входит в этап. Один этап = один экран/блок.
- ❌ Не выдумывать данные, которых нет в БД (см. раздел 4).
- ❌ Не менять существующие немецкие тексты — они взяты из словаря дословно.
  Новые ключи добавлять, старые не переформулировать.
- ❌ Не удалять `data-testid` — на них держатся e2e-тесты.
- ❌ Не делать «похоже». Если не получается один-в-один — написать об этом в отчёте.
