## Этап 2. Docker недоступен

**Дата:** 2026-08-28

Docker Desktop не установлен на машине, где выполняется этап 2. Проверено:

- `docker --version` — `command not found` (Git Bash)
- `docker --version` — команда не распознана (PowerShell)
- `C:\Program Files\Docker\Docker\Docker Desktop.exe` — не существует

Без Docker `supabase start` (локальный Postgres + Auth + Edge Functions в
контейнерах) не поднимается — команда самого CLI это требует. `supabase` CLI
как таковой доступен (установлен через `npx supabase@2.116.0`), это не
блокер сам по себе — блокер именно в отсутствии Docker.

По плану (раздел «Блокеры», подпункт про этап 2) в этой ситуации нельзя
искать обходной путь через боевую базу — гонять e2e там, засоряя данные
команды. Останавливаюсь и жду решения заказчика.

**Варианты, которые предусмотрены планом:**

1. Установить Docker Desktop на этой машине.
2. Завести второй Supabase-проект в той же организации (бесплатный план
   допускает два проекта) и использовать его как изолированную тестовую базу
   вместо локального стека в Docker.

Выбор между ними — за заказчиком, план явно это оговаривает.

## Этап 5. Рабочая ветка не содержит редизайна v2 — план написан для другой ветки

**Дата:** 2026-08-28

Этап 5 предполагает: миграцию `0033_wip_limit_done.sql`, четыре поля в
`app/(app)/admin/WipLimitsForm.tsx` (включая «Erledigt»/`done`), и пункт K5
в `design/redesign-v2/PLAN.md`. Ничего из этого нет в ветке, на которой я
работаю с самого начала (`claude/plan-2026-08-stage-1-4b2a7f`, ответвлена от
`claude/tl-radar-nextjs-setup-g0kqyc`):

- Миграций всего 29, последняя — `0029_wip_limits.sql`. `0030`-`0033` нет
  вообще.
- `WipLimitsForm.tsx` уже сейчас показывает ровно три поля
  (`waiting`/`in_progress`/`paused`, без `done`) — то есть именно то, что
  этап 5 просит СДЕЛАТЬ, здесь уже так и есть, убирать нечего.
- Каталога `design/redesign-v2/` в этой ветке нет вообще (ни `PLAN.md`, ни
  скриншотов) — он существует только в файловой системе как локальные
  файлы в основном чекауте репозитория, не в git-истории этой ветки.

Нашёл, куда делся редизайн v2: он есть в ветке `main` (и `origin/main`,
`origin/claude/redesign-v2-plan-wvtbxo`) — там 33 миграции, `0033` добавляет
`done` в `wip_limits`, `WipLimitsForm.tsx` там на 4 поля, и
`design/redesign-v2/PLAN.md` с пунктом K5 (дословно совпадает с описанием
этапа 5) там присутствует. Точка расхождения (`git merge-base`) — коммит
`0c5a57c` («Этап 15: PWA»): от него `main` ушёл в редизайн v2 (ещё ~10
коммитов, PR #24-28), а ветка `claude/tl-radar-nextjs-setup-g0kqyc` — только
на один служебный коммит («Add files via upload», zip с макетами) вперёд.
Две ветки с этой точки никогда не сливались.

При этом сама система (harness) считает «главной» веткой для PR именно
`claude/tl-radar-nextjs-setup-g0kqyc`, а не `main` — так что это не
случайная опечатка при создании ветки, а действительно две независимые
линии разработки в одном репозитории.

**Почему это блокер, а не повод импровизировать.** План написан явно по
коду ветки `main` (совпадения текстуальные, не просто похожие). Работать
дальше по этапам 5-7 в текущей ветке бессмысленно — либо я буду выполнять
шаги над кодом, которого здесь нет (этап 5), либо описания макетов/экранов
не будут соответствовать тому, что реально на диске (этап 6 ссылается на
`design/redesign-v2/screens/05-slideover-board-dark.png` для этапа 7 — эти
скриншоты тоже есть только на `main`). Слить ветки, перевыполнить этапы
1-4 на `main` или переключить эту сессию на другую ветку — решения с
заметными последствиями (например, если что-то из `main` не должно было
попасть в прод, слияние может это исправить или, наоборот, закрепить).
Не делаю ничего из этого сам.
