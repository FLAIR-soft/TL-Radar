# План: рабочая база — среда, честная документация, закрытые хвосты

## Цель

Редизайн v2 закончен и уехал на боевой сайт, но разработка после него осталась
без опоры: локально проект не запускается, тесты гонять негде, README описывает
библиотеку, которой в проекте нет, а в админке есть настройка, которая ни на что
не влияет.

Эта итерация не добавляет ни одной функции. Она делает так, чтобы следующая
содержательная итерация начиналась с работы, а не с раскопок.

## Что должно работать в конце

Проект собирается и запускается на машине разработчика. E2E-тесты гоняются на
изолированном окружении, боевая база при этом не трогается. README и код говорят
одно и то же. В коде нет сущностей, оставшихся от удалённых решений. В интерфейсе
нет настроек-обманок. Таблица архива помещается в экран. На задачу можно
сослаться коротким номером вместо UUID.

## Контекст

Что нужно знать до начала, чтобы не изучать проект заново.

**Стек:** Next.js 16 (App Router, Server Components, Server Actions, Turbopack),
React 19, TypeScript, Supabase (Postgres + Auth + RLS + Edge Functions + pg_cron).
Хостинг — Vercel, деплой из `main`.

**Стилевых фреймворков нет.** Только `app/globals.css` (~4400 строк) на
CSS-переменных с готовым тёмным вариантом в `:root[data-theme="dark"]`. Tailwind
и UI-киты не используются, графики нарисованы руками на div и svg. Новых
зависимостей не добавлять.

**i18n — главная ловушка.** Тип `Dictionary` выводится из
`lib/i18n/dictionaries/ru.ts`. Любой новый ключ надо добавить сразу в три файла
(`de.ts`, `en.ts`, `ru.ts`), иначе `next build` падает на типах. Глазами это не
ловится, только сборкой.

**Данные** — через серверные компоненты, мутации через `app/(app)/**/actions.ts`.
Клиентского `useEffect + fetch` для данных в проекте нет, и заводить его не надо.

**Ядро приложения — расчёт времени** в `lib/logic/tasks.ts` и `berlin-time.ts`:
рабочее окно 07:30–16:00 по Мюнхену, `effectiveNow()`, вырезание пауз,
`fmtDuration()`. К нему привязаны архив, аналитика и экспорт. В этой итерации
он не трогается вообще.

**Проверка перед каждым коммитом:** `npm run build` и `npm run lint` зелёные.

**Визуал без Supabase** проверяется приёмом из
`design/redesign-v2/PLAN.md`, раздел «Локальный визуальный прогон»: собрать
статический HTML с реальным `app/globals.css` и отрендерить в headless Chromium.

## Перед началом

Две вещи делает заказчик, исполнитель их не может сделать за него.

`.env.local` в корне проекта с тремя значениями из Supabase Dashboard проекта
`tl-radar` (Settings → API): `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

Docker Desktop для второго этапа — без него локальный Supabase-стек не
поднимается.

## Этапы

Каждый этап заканчивается коммитом. Не переходить к следующему, пока предыдущий
не проверен. Этапы 1 и 2 идут строго первыми, остальные — по возрастанию риска.

### Этап 1. Локальный запуск

Папки `node_modules` нет, проект в текущем виде не запускается ничем.

Установить зависимости (`npm ci` — именно `ci`, чтобы взять точные версии из
`package-lock.json`). Убедиться, что `npm run build` и `npm run lint` зелёные на
чистом `main` — это опорная точка, от которой дальше отличать свои поломки от
чужих.

Отдельно проверить безопасность ключей: `.env.local` должен попадать под
`.gitignore`, а `SUPABASE_SERVICE_ROLE_KEY` не должен встречаться нигде, кроме
серверного кода. Он даёт полный обход RLS: если он утечёт в браузер, любой
посетитель сайта получит доступ ко всем данным команды. Проверить поиском по
проекту, что ключ читается только в `lib/supabase/admin.ts` и не импортируется
ни в один файл с `'use client'`.

Дев-сервер на этом этапе смотрит в боевую базу. Пока не готов этап 2, в нём
можно только смотреть: не создавать задачи, не менять статусы, не удалять
ничего — это реальные данные работающей команды.

Проверить: `npm run dev` поднимается, вход по юзернейму и паролю работает,
дашборд показывает боевые задачи, консоль браузера без ошибок.

### Этап 2. Изолированное окружение для тестов

E2E-тесты регистрируют пользователей и создают задачи. Гонять их по боевой базе
нельзя — они засорят данные команды. Сейчас гонять их негде вообще, поэтому
`e2e/golden-path.spec.ts` фактически мёртв.

Поднять локальный Supabase-стек (`supabase start`) и накатить на него все
миграции по порядку. Это заодно первая за долгое время проверка, что миграции
применяются на чистую базу без ошибок — на боевой они накатывались по одной и
годами, воспроизводимость с нуля никто не проверял.

Прогнать `e2e/golden-path.spec.ts` против локального стека. Тесты, которые
падают, разобрать: отличить реальные поломки от устаревших ожиданий после
редизайна.

Записать в README короткую инструкцию: как поднять стек, как прогнать тесты,
какие переменные окружения для этого нужны. Без неё этап придётся повторять
каждый раз заново.

Проверить: `npm run test:e2e` проходит на локальном стеке, боевая база при этом
не получила ни одной новой записи.

### Этап 3. README приводится в соответствие с кодом

В README 488 строк, и как минимум в двух местах (строки 23 и 460) написано, что
графики аналитики рисует `recharts`. Этой библиотеки в проекте нет — её убрали,
графики нарисованы руками. Для человека это мелочь, но следующий исполнитель
прочитает README как источник истины и пойдёт искать несуществующий код.

Пройти документ целиком, а не только два известных места. Сверить с реальностью:
список зависимостей — с `package.json`, структуру каталогов — с тем, что лежит на
диске, число и назначение миграций — с `supabase/migrations`, описания экранов —
с тем, что показывает приложение после редизайна. Упоминания удалённых сущностей
(роль `viewer`, убранные компоненты) — вычистить.

Ничего не досочинять. Если раздел описывает то, чего в коде не найти, и неясно,
что имелось в виду, — раздел удаляется, а не переписывается по догадке.

Проверить: любое утверждение из README подтверждается в коде за минуту поиска.

### Этап 4. Расхождения между кодом и схемой

В коде остались следы удалённых решений. Самый явный: тип `UserRole` в
`lib/supabase/types.ts` до сих пор содержит роль `'viewer'`, хотя её удалила
миграция `0006`. На него опирается `ROLE_RANK` в `lib/logic/access.ts`. Сейчас
это безвредно, но это ровно тот сорт рассинхрона, который однажды выстреливает
в проверке прав доступа.

Пройти системно по четырём направлениям: типы в `lib/supabase/types.ts` против
того, что реально в миграциях; наборы ключей в трёх словарях `de`/`en`/`ru` —
они должны совпадать; экспорты из `lib/logic`, которые никто не импортирует;
компоненты, не подключённые ни к одной странице.

Безопасное чинить сразу в этом же этапе. Спорное — то, где удаление может что-то
сломать, или где неясен замысел, — не трогать, а выписать в
`design/plan-2026-08/findings.md`: что нашлось, почему сомнительно, что
предлагается. Решение по такому списку принимает заказчик, а не исполнитель.

Проверить: сборка и линт зелёные, e2e из этапа 2 проходят, `findings.md` создан
и в нём либо пусто, либо список с обоснованием по каждому пункту.

### Этап 5. Убрать WIP-лимит «Erledigt»

Миграция `0033` добавила четвёртый WIP-лимит для статуса `done`, потому что на
макете админки видно четыре поля. Проблема в том, что колонки «Erledigt» в
канбане не существует: завершённые задачи сразу уезжают в архив. Лимит
настраивается и сохраняется, но физически ни на что не влияет. Тимлид выставит
там число и будет считать, что оно работает.

Настройка, которая делает вид, что работает, хуже отсутствующей настройки.
Убрать четвёртое поле из формы в `app/(app)/admin/WipLimitsForm.tsx`.

Миграцию `0033` не откатывать и строку `done` из таблицы `wip_limits` не
удалять: данные безвредны, а откат миграции на боевой базе — риск ради нуля.
Оставить в файле миграции комментарий, что поле убрано из интерфейса, и почему.

В `design/redesign-v2/PLAN.md` пометить пункт K5 как отменённый, с причиной —
чтобы следующий исполнитель, сверяясь с макетом, не вернул поле обратно.

Проверить: в админке три поля, сохранение лимитов работает, WIP-лимиты на борде
по-прежнему срабатывают, в базе ничего не изменилось.

### Этап 6. Таблица архива помещается в экран

Десять колонок дают около 1357px при доступных примерно 1156px на экране
1440px — таблица прокручивается вбок. Так было и до редизайна, это не регресс,
но каждый день это мешает.

Цель: таблица помещается по ширине на 1440px без горизонтальной прокрутки, и при
этом ни одно значение не пропадает с экрана.

Предлагаемый подход: три временные отметки — создана, начата, завершена — сейчас
занимают три колонки, хотя читаются как одна группа. Свести их в одну колонку
«Zeiten» с тремя строками моно-цифрами (класс `.mono` уже с `tabular-nums`).
Этого должно хватить; если нет — сокращать дальше по тому же принципу, объединяя
родственные значения, а не выбрасывая их.

Экспорт CSV и XLSX не трогать: там колонки остаются как есть, выгрузка идёт в
таблицу и в ширину экрана не упирается. `data-testid` сохранить все — на них
держатся e2e.

Проверить: скриншот при 1440px без горизонтальной прокрутки в светлой и тёмной
теме, все десять значений на месте, e2e зелёные, выгрузка CSV и XLSX побайтово
не изменилась.

### Этап 7. Человекочитаемый номер задачи

У задачи сейчас только UUID. Сослаться на неё голосом или в переписке
невозможно. На эталонном макете панели задачи строка `AUFGABE #412` есть, и в
коде на её месте стоит комментарий, что номера в базе нет
(`TaskDetailPanel.tsx`, около 185-й строки). То есть дизайн это предусматривал, а
данных под это нет.

Этап единственный в итерации, который меняет схему боевой базы. Порядок жёсткий:
сначала согласовать, потом делать.

Посмотреть, как оформлены существующие миграции, и повторить их стиль и
нумерацию — следующая свободная `0034`. Предложить миграцию: колонка
`task_number` в `tasks`, заполнение для существующих строк в порядке
`created_at`, затем `NOT NULL` и автоприсвоение для новых. Показать текст
миграции заказчику и дождаться явного «да» — только после этого применять к
боевой базе.

Номер должен быть стабильным навсегда. Не выводить его на лету из UUID, из
`created_at` или из позиции в списке.

Показывать в панели задачи как `AUFGABE #N` по макету
`design/redesign-v2/screens/05-slideover-board-dark.png`. Нужен ли номер ещё
где-то — в архиве, на карточке, поиском по номеру в командной палитре — спросить
заказчика отдельно, не решать самому.

Обновить `lib/supabase/types.ts`.

Проверить: у всех существующих задач есть номер, номера идут по порядку создания
и не повторяются; новая задача получает следующий номер; после перезагрузки
страницы номер тот же.

## Что не делать в этой итерации

- Новые функции и новые экраны
- Любые правки логики времени: `fmtDuration`, `fmtTimer`, `effectiveNow`,
  правила переходов статусов, расчёт пауз, рабочее окно. Если этап потребовал
  их тронуть — это блокер, а не повод
- Новые зависимости, Tailwind, UI-киты, библиотеки графиков
- Хардкод цветов мимо CSS-переменных
- Удаление `data-testid`
- Прогон e2e по боевой базе
- Применение любой миграции к боевой базе без явного «да» заказчика
- Откат миграции `0033`

## Блокеры

Если упираешься во что-то, чего план не предусмотрел, — остановись и опиши
проблему в `design/plan-2026-08/blockers.md`. Не импровизируй в обход плана.

Отдельно про этап 2: если Docker недоступен и локальный стек не поднимается — не
искать обходные пути через боевую базу. Описать проблему и остановиться. Запасной
вариант существует (на бесплатном плане Supabase разрешено два проекта в
организации, второй свободен и денег не стоит), но выбор между ним и Docker
делает заказчик.

Отдельно про этап 6: если таблица не помещается даже после объединения колонок —
не сокращать содержимое молча. Описать, какие варианты остались и чем каждый
платит.

Отдельно про этап 7: миграция применяется к боевой базе только после явного
подтверждения. Если что-то в предложенной схеме вызывает сомнение — сказать до
применения, а не после.

## Отчёт по каждому этапу

В конце этапа показать: что сделано по пунктам; результат `npm run build` и
`npm run lint`; скриншоты до и после, если этап трогал интерфейс; что не удалось
