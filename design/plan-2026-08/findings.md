# Находки этапа 4 (расхождения кода и схемы)

Проверено по четырём направлениям из плана: типы vs миграции, три словаря
i18n, неиспользуемые экспорты `lib/logic`, компоненты без подключения к
странице. Безопасные вещи почищены сразу в этом же коммите (см. ниже, для
контекста находки). Здесь — только то, что не тронул, потому что не мне
принимать решение.

## 1. Роль `viewer` — план был не совсем точен, реального бага не нашёл, но домен до конца не закрыт

**Что нашлось.** План предполагал, что миграция `0006_remove_viewer_role.sql`
«удалила» роль `viewer`, и `UserRole` в `lib/supabase/types.ts` — рассинхрон
с этим. Проверил содержимое `0006` построчно — это не так:

```sql
update profiles set role = 'editor' where role = 'viewer';
alter table profiles alter column role set default 'editor';
```

Миграция переносит существующие строки и меняет default. Сам Postgres-enum
`user_role` (`create type user_role as enum ('viewer', 'editor', 'admin');`
из `0001_init.sql`) ни разу за все 29 миграций не пересоздаётся — `viewer`
как значение домена **по-прежнему легален на уровне схемы**. TypeScript-тип
`UserRole = 'viewer' | 'editor' | 'admin'` в этом смысле точно отражает
реальную БД, а не расходится с ней.

Показательное сравнение: когда из проекта убирали язык `el` (греческий),
миграция `0016_remove_greek_locale.sql` сделала это правильно —
`update ... where locale = 'el'`, затем `drop constraint` + пересоздание
`check` уже без `'el'`, так что БД с этого момента физически отклоняет
`'el'` при записи. Для `viewer` аналогичного второго шага не было. То есть
авторы проекта явно умеют закрывать домен до конца — здесь просто не
закрыли.

**Почему не тронул.** Оставленный как есть код безопасен: `ROLE_RANK` в
`lib/logic/access.ts` содержит запись для всех трёх значений enum, и если
бы строка с `role = 'viewer'` существовала, `canViewStats('viewer')`
корректно вернул бы `false` — не крашится и не даёт лишний доступ. Живого
бага нет. Но я не смог проверить, есть ли на боевой базе профили с
`role = 'viewer'` — прямой запрос к продакшену через сервисный ключ
заблокировал классификатор безопасности сессии, а без такой проверки
я не могу быть уверен, что уборка типа/enum ничего не сломает.

**Что предлагается.** Два независимых решения, оба не обязательны прямо
сейчас:

1. Быстрая проверка (10 секунд): в Supabase Dashboard → Table Editor →
   `profiles`, отфильтровать по `role = viewer`. Если пусто — можно со
   спокойной совестью считать домен фактически закрытым (хотя формально
   enum всё ещё это разрешает).
2. Если хочется закрыть домен по-настоящему, как для `el` — отдельная
   миграция, пересоздающая enum без `viewer` (в Postgres это либо
   `create type ... rename`, либо колонка на `text` + `check`), плюс синхронно
   убрать `'viewer'` из `UserRole` в `lib/supabase/types.ts` и из
   `ROLE_RANK`. Это меняет боевую схему — по правилам этого плана такое
   делается только после явного «да» заказчика (как этап 7), поэтому не
   делаю сам.

## Что почищено сразу (безопасно, без последствий для схемы/поведения)

- `lib/logic/icons.ts`: удалена функция `resolveIcon` — не вызывалась нигде
  в проекте, включая сам файл (весь код использует `isIconName` + `ICON_MAP`
  напрямую).
- `lib/logic/recurring.ts`: убран дублирующий `type RecurringFrequency`
  (identичный по составу тип уже есть и используется как единственный
  источник истины в `lib/supabase/types.ts`); файл теперь импортирует его
  оттуда вместо повторного определения.
- Остальные «экспорты без внешних импортов», которые нашлись при поиске
  (`STATS_MIN_ROLE`, `VALID_KANBAN_TRANSITIONS`, `TaskFilters`,
  `MentionSegment`, `DeadlineFilter`, `berlinOffsetMs`) — проверил каждый:
  это либо специально вынесенные именованные константы для будущих правок
  (`STATS_MIN_ROLE`, `VALID_KANBAN_TRANSITIONS` — прямо так и описаны в
  README/комментариях), либо обычные вспомогательные типы/функции, нужные
  только внутри своего файла — нормальный паттерн, не находка.
- Три словаря (`de`/`en`/`ru`) — структурно идентичны, 331 ключ в каждом,
  один в один. Компоненты — все 17 файлов в `components/` подключены хотя
  бы к одной странице. По этим двум направлениям находок нет.
